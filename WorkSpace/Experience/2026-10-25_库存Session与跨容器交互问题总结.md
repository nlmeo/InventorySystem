# 2026-10-25 库存 Session 与跨容器交互问题总结

## 背景

本轮将库存 UI 统一到 `UINV_InventorySessionWidget`：Session 作为唯一 Viewport 根节点，持有玩家背包子 UI 和来源侧 UI。玩家按 `I` 时只切换 Session 内的玩家背包子 UI；容器、掉落包、弹挂和尸体复用来源 UI。

同时移除了 `UINV_SpatialInventory::RebindInventoryForSession()`，玩家网格只在自身初始化阶段绑定玩家 `InventoryComponent`，避免 Session 重挂载时重复绑定、重复创建和重复加入 Viewport。

## 问题一：容器网格能打开、高亮正常，但物品放不进去

### 原因

拖拽开始时，Slate 拖拽操作 Payload 与网格内部临时 Payload 是两个对象。Session 重挂载、来源切换或拖拽生命周期变化后，Payload 中的 `SourceInventory` 可能为空、过期或指向目标库存。

### 解决

- 目标网格根据当前活动来源库存和玩家库存的实际条目归属重新解析来源。
- 如果来源等于目标组件，则回到同库存移动/交换路径。
- 装备槽拖拽没有 `SourceInventory`，直接回到装备卸下路径。
- 容器网格的普通操作不再直接对容器 Actor 发起组件 RPC。

## 问题二：自动旋转后拖拽图标、高亮和服务器落点不一致

### 原因

源网格内部 Payload、Slate 拖拽操作 Payload、目标网格外部 Payload 三者不同步。自动试转只更新了源网格临时状态，跨容器提交又曾使用鼠标事件的原始 `GridIndex`，没有使用预览阶段计算出的 `ItemDropIndex`。

### 解决

- 源网格保存拖拽操作 Payload，并在自动旋转时同步操作 Payload 的旋转状态。
- 目标网格绑定外部 Payload 后立即同步拖拽图标的 RenderTransform。
- 松手时重新执行最终空间查询，提交 `ItemDropIndex` 而不是原始鼠标格索引。
- 服务器继续复核最终 Slot、Index、尺寸和旋转。

典型错误是 10 列网格中提交 `Index=19`，该索引位于第 9 列，`2×3` 物品必然越界。

## 问题三：服务器 Transfer 成功，但客户端 SourceGrid 不刷新

### 原因

库存条目 `UINV_InventoryItem` 是注册复制子对象。容器 Actor 只设置了 `bReplicates=true`，没有启用注册子对象列表，导致新创建的容器条目没有复制到客户端。重复 `ScheduleRefresh()` 只能重铺客户端当前仍为空的列表。

### 解决

- `AINV_TestContainer` 启用 `bReplicateUsingRegisteredSubObjectList=true`。
- `UINV_InventoryComponent::ReadyForReplication()` 注册已有库存条目。
- 容器操作回执到达客户端时，同时刷新玩家库存和活动容器库存。
- 移除客户端自动重试刷新机制，避免用重复刷新掩盖复制问题。

## 问题四：容器 Actor 上出现 No owning connection

### 日志

```text
UNetDriver::ProcessRemoteFunction: No owning connection for actor ABP_Container_C...
Function Server_SubmitInventoryOperation will not be processed.
```

### 原因

跨容器请求已经由玩家控制器的服务器 RPC 接收，但服务器处理阶段又调用了容器组件的客户端 `Server_SubmitInventoryOperation`。容器 Actor 没有玩家 owning connection，嵌套 RPC 会被 Unreal 丢弃。

### 解决

跨容器 Transfer 统一走：

```text
InventoryGrid / SourceWidget
→ PlayerController
→ ServerContainerTransfer
→ SubmitInventoryOperationFromServer
→ ProcessInventoryOperation
```

容器网格的移动、旋转、批量移动、合并、拆分、使用等普通操作也增加了通用 `ServerContainerOperation` 路径。当前活动容器网格通过 PlayerController 转发，普通玩家背包继续使用玩家库存组件自己的入口。

## 问题五：前两次请求看似成功，第三次才真正执行

### 表现

前两次日志有 `Failure=0`，但没有完整的服务器事务完成日志；第三次才出现 `事务提交后状态`、`处理完成`、`SourceItems=0` 和 `TargetItems=1`。

### 原因

服务器内部容器请求复用了 `NextClientRequestId`。第一次和第二次请求使用的 RequestId 已经存在于 `CompletedOperations`，服务器将其识别为旧请求并重放旧结果，因此返回旧的 `Failure=0`，没有执行新事务。

### 解决

客户端普通操作继续使用低位 RequestId；玩家控制器转发到服务器的容器操作使用独立的高位 RequestId 命名空间：

```cpp
NextServerRequestId = 1LL << 60;
```

这是本轮“需要连续拖放多次”的根本原因。

## 问题六：服务器回执与客户端快照时序不稳定

### 原因

`DeliverOperationResult()` 在服务器权限分支中曾直接调用 `_Implementation`，只更新服务器对象，没有真正向远端客户端发送 Client RPC。跨容器又有 PlayerController 回执，两个刷新来源的顺序可能不同。

### 解决

- 远程模式下调用真正的 `Client_InventoryOperationCompleted()` RPC。
- 只有 Standalone 模式使用 `_Implementation` 直接刷新。
- 客户端以 RequestId、Revision、CompletionSequence 过滤旧结果。

- UHT 通过。

- 客户端自动刷新重试已移除。

## 后续排查准则

遇到跨容器异常时，按以下顺序看日志：

1. 是否有 `提交拖放`。
2. 是否有 `客户端发送请求`。
3. 是否有 `服务器内部提交`，并确认 RequestId 是否为高位服务器编号。
4. 是否有 `开始处理` 和 `处理完成`，不要只看 `Failure=0`。
5. 检查 `SourceItems`、`Source仍含Item`、`TargetItems`。
6. 检查 FastArray 条目是否到达客户端，再判断 UI 是否重铺。

只看到 `Failure=0` 而没有对应 RequestId 的“处理完成”日志时，应优先怀疑旧结果重放或错误的 RPC 路径，不能把它当作本次事务成功。

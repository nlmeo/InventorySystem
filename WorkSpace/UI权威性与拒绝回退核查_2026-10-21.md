# UI 权威性、悲观提交与拒绝回退核查

2026-10-22 修复进展：超容量合并、负数使用已在 #4.1 第一批修复并加入硬断言；最新 8 项自动化通过，对应两个审计风险值为 false。其它架构风险仍未解决。下文保留初次核查结果，最新实现见 [服务端数量与边界校验](服务端数量与边界校验_2026-10-22.md)。

## 结论

当前是**服务器最终处理操作 + 混合 UI + 部分权威快照纠正**，不是完整的“服务器权威 + 悲观 UI”，也没有完整的“乐观 UI + 客户端预测 + 操作级回滚”。

`BP_INV_InventoryComponent` 默认 `bServerAuthoritativeUI=true`。但该开关没有覆盖全部本地修改路径，因此不能仅凭开关名判断策略；服务端有校验也不等于校验条件已完整。

本次核查没有切换开关、修改运行时行为或保存蓝图资产。新增隔离验证测试、只读资产检查脚本，并修正了开关注释中与实现不符的描述。

## 各操作实际行为

| 操作 | 当前开启模式下的行为 | 判断 |
| --- | --- | --- |
| 拾取、拾取即装备 | 服务器选址、定量、写装备状态，再复制表现 | 主要为悲观提交 |
| 合并、填充、满堆数量互换 | 本地主要只发请求，不先改两堆数量 | 主要为悲观提交 |
| 拆分、使用 | 不先扣本地数量；拆分由服务器选址与朝向 | 主要为悲观提交 |
| 移动、交换、旋转、重排 | 先清格、铺图标、写本地物品字段，再发 RPC | 存在乐观预写 |
| 丢弃 | 发 RPC 后立即清本地格子及位置，再请求刷新 | 存在乐观预写 |
| 装备、卸下、装备槽互换 | 先改槽位、朝向和装备标记，再发请求，部分组合使用多条 RPC | 存在乐观预写及非原子链路 |
| 鼠标高亮和拖拽图标 | 使用 Payload 临时朝向和候选落点 | 合理的本地预览，本身不应等同于修改已确认库存 |

## 已验证正确的部分

- 服务器拒绝单件占用冲突时，在未被客户端预写污染的权威状态上保留旧索引，并恢复试验朝向。
- 批量移动冲突拒绝时，本次测试中的两个位置和朝向保持原值。
- 收到快照后，已存在于本地列表的条目能够恢复容器、索引、数量、fragment 数量、朝向与装备槽标记，并排队通知重绘。
- 移动、交换、批量移动等现有调用会在操作 RPC 后请求快照；同一组件上的 Reliable 请求顺序有助于服务器先处理操作再生成回复。

这证明字段纠正机制可用，不证明全部操作、真实远端网络或完整界面恢复已经正确。

## 未通过的检查与缺口

### 1. 单机 / 监听服共享对象预写，拒绝后不能保证恢复

`UpdateGridSlots`、`RemoveItemFromGrid`、朝向应用等函数会直接改 `InventoryItem`。本机权威下客户端表现与服务器持有同一份对象；随后服务器校验时，“旧状态”可能已经是 UI 预写后的值。

`RequestAuthoritativeRefresh` 在本机权威分支仅安排重绘，没有独立的已确认基线。隔离探针模拟同样的预写后再提交被阻挡的移动，拒绝后索引和朝向仍保留预写值。

建议：确认态与临时表现分离，或收敛为提交前不写确认态；不能指望把同一个被改过的对象重画一遍就完成回滚。

### 2. 装备失败缺少统一回执和强制纠正

空槽装备和装备槽互换会先改本地表现及物品字段，但 `BroadcastSlotClickedDelegates` / `BroadcastEquippedItemMoved` 不统一请求权威快照。服务器提前 return 且状态未变化时，正常复制不保证重新发送原值，客户端可能继续保留错误预测。

建议：所有请求返回成功 / 拒绝及权威结果；拒绝路径也必须可靠结束本地等待状态、恢复已确认表现。

### 3. 换装 / 卸下使用多条 RPC，快照无法撤销服务器部分提交

已复现：先成功装备新物品并卸下旧物品，再回填旧物品时被服务器拒绝。此时新物品已装备，旧物品仍在库存列表中，但没有容器、没有网格索引，也不在装备槽中。

这种情况读取服务器快照只会读回已部分提交的状态。需要整体预检和原子提交，或明确的服务器端补偿事务，不能只修客户端重绘。

### 4. 快照没有操作关联和版本保护

快照只覆盖已匹配条目的字段，不负责增删 InventoryList；条目成员关系仍依赖 FastArray。没有 RequestId、已确认 Revision、待确认操作队列或预测重放。

手工先应用新快照、再应用旧快照，会被旧值覆盖。这项探针证明没有过期防护，**不是声称已复现同一 Reliable RPC 通道乱序**。即便回复有序，较早操作的回复仍可能覆盖客户端后来尚未确认的预测。

### 5. 关闭当前开关不能获得完整的乐观预测回滚

`bServerAuthoritativeUI=false` 时，`RequestAuthoritativeRefresh` 和 `NotifyItemReplicatedChange` 会提前返回。探针确认不安排纠正刷新。旧的本地预写分支仍存在，但没有完整预测日志、操作确认与拒绝恢复，不应直接作为正式乐观模式启用。

### 6. 附加发现：服务端数量校验仍有缺口

- 目标 9、上限 10，源 4，直接请求合并 4 后目标变成 13，服务器没有拒绝或限制超上限转入量。
- 直接请求 `Server_UseItem(Item, -1)` 会增加库存数量。
- 这些在隔离测试世界中已复现，正常菜单不一定会发出这些参数，但服务器本身应拒绝非法数量。还应统一检查同一物品自合并、丢弃正数/上限、源目标归属和装备槽约束。
